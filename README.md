# charchat-lab

[![tests](https://github.com/chisu0208/charchat-lab/actions/workflows/tests.yml/badge.svg)](https://github.com/chisu0208/charchat-lab/actions/workflows/tests.yml)

캐릭터 채팅 서비스가 속에서 어떻게 돌아가는지 직접 만져 보는 로컬 실험실이에요.
모델을 만드는 게 아니라, 모델 API 위에 얹는 부분(프롬프트 조립, 기억 관리, 캐시, 검수)을 구현하고 계측합니다.
기본 설정은 전체이용가 기준이에요.

- **API 키 없이 시작**: mock 제공사가 답변과 Anthropic식 프롬프트 캐시, 지연 시간까지 흉내 내요.
- **실제 모델 연결**: Claude, Gemini, OpenAI 호환 서버(Ollama, LM Studio, llama.cpp, vLLM 등)를 설정만 바꿔 끼워요.
- **매 턴 계측**: 프롬프트 구성(추정 토큰), 실제 사용량과 캐시 적중, 첫 토큰 지연, 비용, 로어 주입, 대화 창 상태를 오른쪽 패널에서 봐요.

## 빠른 시작

Python 3.10 이상이 필요해요.

**Windows (PowerShell)**

```powershell
cd charchat-lab
py -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
Copy-Item .env.example .env
.venv\Scripts\python run.py
```

**macOS / Linux**

```bash
cd charchat-lab
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env
.venv/bin/python run.py
```

브라우저에서 <http://127.0.0.1:8000> 을 열어요. 처음 실행하면 샘플 캐릭터 둘(고서점 주인 '하람', 정거장 정비 로봇 '에코')이 들어가 있어요.
데이터는 `data/lab.sqlite3`에 저장돼요. 처음부터 다시 하고 싶으면 서버를 끄고 이 파일을 지우면 돼요.

개발하면서 코드 수정을 바로 반영하려면 `uvicorn app.main:create_app --factory --reload`로 실행하세요.

## 실제 모델 연결

`.env`를 고치고 서버를 다시 시작한 뒤, 화면의 **설정**에서 제공사를 고르면 돼요.

| 제공사 | .env에 넣을 것 | 참고 |
|---|---|---|
| Claude | `ANTHROPIC_API_KEY`, (선택) `ANTHROPIC_MODEL` | 기본 모델 `claude-haiku-5-5`, `ANTHROPIC_EFFORT=low` |
| Gemini | `GEMINI_API_KEY`, (선택) `GEMINI_MODEL` | 기본 모델 `gemini-3.8-flash`, `GEMINI_THINKING_LEVEL=low` |
| Ollama 등 | `OPENAI_COMPAT_BASE_URL=http://localhost:11434/v1`, `OPENAI_COMPAT_MODEL` | 키 없이 동작, 사고는 숨기고 분량·시간만 표시 |

제공사별로 알아 둘 점 (2026년 10월 공식 문서 기준)

- **현행 Claude 모델**(Haiku/Sonnet/Opus 5.5 등)은 temperature·top_p·top_k를 기본값이 아닌 값으로 보내면 400 오류가 나요. 그래서 이 앱은 Claude에는 temperature를 보내지 않아요.
- 현행 Claude 모델은 **사고(thinking)가 기본으로 켜져** 있고, 사고 토큰도 `max_tokens`에 포함돼요. 답변이 잘리지 않게 `ANTHROPIC_THINKING_HEADROOM`(기본 2048)만큼 더해서 보내요. 첫 토큰을 빠르게 하려면 `ANTHROPIC_EFFORT=low`를 쓰거나, Haiku 5.5라면 `ANTHROPIC_THINKING=disabled`를 써 보세요.
- **Claude 캐시 최소 길이는 512토큰**(현행 모델)이에요. 그보다 짧은 앞부분은 `cache_control`을 붙여도 오류 없이 캐시되지 않아요.
- **Gemini**는 조정 가능한 안전 필터가 기본으로 꺼져 있어서, 이 앱은 `GEMINI_SAFETY_THRESHOLD=BLOCK_MEDIUM_AND_ABOVE`로 네 범주를 켜서 보내요. 사고 토큰은 `max_output_tokens`에 포함되므로 여기도 여유분을 더해요. 캐시는 자동(암묵적)으로만 동작하고, 3.8 Flash 기준 앞부분이 4,096토큰 이상 같아야 적중해요.
- Gemini API 약관상 18세 미만이 이용할 가능성이 높은 서비스에는 쓸 수 없어요. 혼자 쓰는 로컬 실험은 괜찮지만, 공개한다면 약관부터 다시 확인하세요.
- **추론형 로컬 모델**(Qwen 3.5 등)은 사고가 기본으로 켜져 있어요. `OPENAI_COMPAT_REASONING_EFFORT=none`으로 끌 수 있어요(Ollama, vLLM, OpenAI가 받아요). 작은 모델일수록 끄는 편이 나았어요(실험 8). Ollama 0.40.16은 qwen3.5에 `low`·`medium`·`high`를 구분하지 않고 모두 '사고 켬'으로 다뤄요. `low`로도 짧은 질문 하나에 사고 2만 자를 썼어요.
- **Ollama의 `/v1`** 은 temperature·top_p를 안 보내면 모델 기본값 대신 1.0을 써요. `ollama show 모델이름 --parameters`로 기본값을 보고 `OPENAI_COMPAT_TOP_P`로 맞춰 보내세요. 다만 qwen3.5에서 `top_p`·`presence_penalty`를 Modelfile 값으로 맞춰 보내 봤을 때 한자 섞임은 줄지 않았어요(실험 8).
- 사고는 서버가 따로 보내면(Ollama의 `reasoning`, vLLM·LM Studio의 `reasoning_content`) 그 필드로 받고, 본문에 `<think>…</think>`로 섞여 오면 걸러서 숨겨요. 여는 태그 없이 `</think>`만 오면 그 앞을 사고로 보고 화면에서 지워요.
- Ollama의 컨텍스트 길이(`ollama ps`의 CONTEXT 열)가 입력 예산 + 최대 출력보다 작으면 프롬프트 앞부분이 오류 없이 잘려요. 반대로 너무 크면 VRAM을 많이 차지하니 `OLLAMA_CONTEXT_LENGTH`로 맞추세요. 기본값은 모델 최대치(qwen3.5는 262,144)라서, 8GB GPU에서 qwen3.5:4b는 14.3GB 중 5.4GB만 VRAM에 올라가고 나머지는 시스템 메모리로 밀려나요. 8,192로 줄이면 3.4GB로 모두 올라가서 프롬프트 처리가 약 2.4배, 생성이 약 1.9배 빨라졌어요. 2b는 VRAM만 5.8GB에서 2.5GB로 줄고 속도는 같았어요.

## 화면

- **왼쪽**: 캐릭터와 대화 목록. 캐릭터 카드(JSON, PNG)를 가져오거나 내보낼 수 있어요. SillyTavern 등에서 쓰는 Character Card V2/V3 형식이에요.
- **가운데**: 대화. 답변마다 `‹ 1/2 ›`로 다시 생성한 버전이나 고쳐 쓴 가지를 넘겨 볼 수 있어요. **멈춤**을 누르면 화면에 보인 만큼 저장돼요.
- **오른쪽 패널**
  - **이번 턴**: 프롬프트 구성 막대(고정/요약/대화/마지막 입력), 실제 입력 토큰과 캐시 읽기·쓰기, 추정 대비 실측 비율, 사고 분량과 시간, 비용, 지연 시간, 답변 품질(어림), 대화 창, 로어북, 보낸 요청 원문
  - **비교**: 같은 대화의 턴을 실행 조건별로 묶어 평균 입력, 캐시 적중률, 비용, 첫 토큰, 첫 표시를 나란히. 실험 라벨, 모델, 창 전략, 입력 예산, 캐시 방식, 출력 버퍼, .env의 사고 설정, 프롬프트 파일 중 하나라도 다르면 행이 나뉘고, 설정 칸에는 행마다 다른 조건만 보여요. 비용은 대화에 요약과 LLM 검수 판정 호출을 더한 합계예요. 외국 문자·반복·말투 변화 칸은 답변 품질 어림 지표의 평균이에요(외국 문자 칸에는 한 글자라도 낀 턴 수도 함께 나와요). 첫 토큰·첫 표시 칸에는 평균과 중앙값이 같이 나오는데, 로컬 모델은 첫 턴에 모델을 메모리에 올리는 시간이 평균을 크게 부풀려서(2b 모델의 첫 턴이 81초였어요) 중앙값이 실제 속도에 더 가까워요
  - **요약**: 지금 쓰이는 요약과 수동 요약 버튼
  - **검수 로그**: 어디서(입력/출력/카드), 무엇에, 어떻게(막음/기록/가림/위기 안내) 걸렸는지
  - **실험**: 대본 재생 실험의 목록, 진행 상황, 변형별 결과 비교. 대화를 고르지 않아도 보여요

mock 제공사에서는 입력에 테스트 명령을 넣을 수 있어요: `/long`(긴 답변), `/mod-test-output`(출력 검수 테스트), `/error`(스트리밍 도중 오류), `/slow`(느리게), `/think`(사고 흉내), `/think-leak`(사고가 답변으로 샜다가 지워짐), `/quality-test`(한자·영어가 섞인 대사와 똑같은 문장 세 번을 붙여 답변 품질 깃발 확인).

답변 아래와 이번 턴 탭의 **답변 품질**은 글자 모양과 어미만 보는 어림 지표예요. 한자·가나 같은 외국 문자 비율(1% 이상이면 '외국 문자'), 로마자 비율(5% 이상이면 '영문 섞임'), 대사의 존댓말·반말이 직전 답들과 뒤바뀌었는지('말투 변화'), 직전 답과 겹친 글자 5-gram 비율(40% 이상)이나 같은 답 안에서 되풀이한 문장 비율(30% 이상)('반복'), 답에 프롬프트의 장치(`<system-memo>`처럼 `final_user.txt`에 쓰인 태그, 풀지 못한 `{{매크로}}`, 채팅 템플릿 토큰)가 그대로 나온 것('프롬프트 샘')을 봐요. 태그는 덮어쓴 템플릿을 따라가요. 큰따옴표를 닫지 않은 답(작은 모델에서 흔해요)은 대사를 따로 가려내지 못해서 묘사를 뺀 글 전체의 어미를 봐요. 판단은 직접 읽고 하세요. mock 답변은 정해진 문장 조각을 이어 붙여서 '반복' 깃발이 자주 떠요.

## 대본 재생 실험

같은 입력 목록(대본)을 설정만 바꿔 여러 번 보내는 일을 자동으로 해요. 오른쪽 패널의 **실험** 탭에서 **새 실험**을 누르세요.

- **입력 대본**: 한 줄에 하나씩 보낼 말을 적어요(최대 100개, 빈 줄은 건너뜀).
- **변형**: 라벨과, 지금 설정에서 바꿀 값만 적은 설정 JSON이에요(최대 6개). 예: `{"window_strategy": "full"}`, `{"input_token_budget": 3000}`, `{"provider": "openai_compat", "models": {"openai_compat": "qwen3.5:4b"}}`. 변형마다 새 대화를 만들어 대본을 처음부터 보내고, 라벨이 실험 라벨이 되어 결과 표의 행을 나눠요. 저장된 설정은 바뀌지 않아요.
- **제공사 옵션과 프롬프트도 변형마다**: `.env`로만 바꾸던 사고·샘플링 옵션과 `prompts/*.txt`의 내용도 변형의 설정 JSON으로 덮어쓸 수 있어요. 서버를 다시 켜지 않아도 실험 한 번에 비교돼요.
  - `{"provider_options": {"openai_compat": {"reasoning_effort": "none", "top_p": 0.95}}}`: 바꿀 수 있는 옵션은 Claude의 `effort`·`thinking`, Gemini의 `thinking_level`, OpenAI 호환의 `reasoning_effort`·`top_p`·`presence_penalty`예요. 값을 `null`로 두면 `.env`에 값이 있어도 보내지 않아요. Ollama의 `/v1`은 `top_p`·`presence_penalty`를 보내지 않으면 Modelfile의 값(`ollama show 모델 --parameters`) 대신 1.0·0을 써요.
  - `{"prompt_overrides": {"final_user": "<system-memo>\n{lore}{instructions}\n</system-memo>\n\n{input}"}}`: 파일 이름(확장자는 빼도 돼요)과 바꿀 내용이에요. `final_user`에는 `{input}`, `summary_user`에는 `{dialogue}`가 있어야 해요. 요약·검수 프롬프트도 같은 방식으로 바꿀 수 있어요.
  - 덮어쓴 값은 실행 조건(제공사 옵션, 프롬프트 지문)에 그대로 남아서 비교 표의 행이 저절로 나뉘어요. 같은 키를 `PUT /api/settings`로 저장해 두면 평소 대화에도 쓰여요(설정 화면에는 나오지 않아요).
- **mock 캐시 비우고 난수 다시 심기**: 변형마다 mock을 같은 상태(같은 시드)에서 시작해요. 설정이 같으면 답변과 캐시 적중이 똑같이 나와서, 설정 차이만 비교할 수 있어요.
- **요약 기다리기**: 매 턴 요약이 끝난 뒤 다음 입력을 보내요. 요약이 늦어 다음 턴이 잘리는 일(overflow)이 결과를 흔들지 않게 해요.
- **대화 사이 대기**: 실제 제공사의 캐시는 비울 수 없어요. 앞 대화의 캐시가 뒤 대화에 섞이지 않게 하려면 캐시 수명보다 길게 기다리세요(Anthropic 기본 5분).
- **반복**: 같은 대본을 변형마다 최대 5번 돌려요. 1회차에 모든 변형, 2회차에 모든 변형 순으로 번갈아 돌아서, 시간에 따라 바뀌는 조건(로컬 모델이 메모리에 올라와 있는지 등)이 한 변형에만 몰리지 않아요. mock은 회차마다 시드를 하나씩 바꾸고, 같은 회차의 변형끼리는 같은 시드를 써요. 결과 표 아래 **반복 사이 편차**에 끝까지 돈 대화 하나를 표본 하나로 본 평균과 표준편차가 나와요. 변형 사이의 차이가 표준편차보다 충분히 커야 설정의 차이라고 볼 수 있어요.

결과 표는 비교 탭과 같은 모양이고(반복한 회차의 턴은 한데 모아 세요) **CSV로 내려받기**로 받을 수 있어요. 반복한 실험의 CSV에는 행마다 반복 수(`runs`)와 반복 사이 표준편차(`…_sd`)가 붙어요. 변형마다 만든 대화는 왼쪽 목록에 `[실험] 이름 · 라벨`(반복하면 `· 2회`처럼 회차까지)로 남고, 실험 탭의 **대화 열기**로 바로 열 수 있어요. 실제 제공사로 보내는 변형이 있으면 시작하기 전에 변형별 호출 수와 비용 상한을 보여 주고 한 번 물어요. 상한은 매 턴 입력 예산과 최대 출력을 모두 쓴다고 본 값이라 실제보다 크고, 캐시 할인과 요약 비용은 빠져 있어요. 가격표에 없는 모델은 비용 없이 호출 수만 나와요. 같은 모델로 보내는 실제 제공사 대화가 둘 이상(같은 모델의 변형이 여럿이거나 반복)인데 대화 사이 대기가 5분보다 짧으면, 앞 대화의 캐시가 뒤 대화에 섞인다는 경고도 함께 나와요(캐시는 모델마다 따로라서 모델이 다른 변형끼리는 괜찮아요).

실험은 한 번에 하나만 돌아요(mock의 캐시와 난수를 모든 대화가 함께 쓰기 때문이에요). mock 변형이 있는 실험이 도는 동안 mock으로 다른 대화를 보내면 난수 순서가 섞이므로, 서버가 409로 막아요. 끝나거나 취소한 뒤에 보내세요. 검수에 막힌 입력은 '막힘'으로 세고 다음 입력으로 넘어가며, 제공사 오류가 나면 그 대화만 멈추고 다음 대화(변형이나 회차)로 넘어가요. 중간에 멈춘 대화는 반복 사이 편차의 표본에서 빠져요. 서버를 끄면 진행 중이던 실험은 '서버가 꺼져 끊김'으로 남아요.

**실험 2를 실행기로 하기**: 새 실험 대화상자에서 **실험 2 예시 채우기**를 누르면 하람, 16줄 대본, 변형 셋(`full`, `sliding`, `anchored`, 모두 입력 예산 3000)이 채워져요. 그대로 시작하면 실험 탭에 세 행이 나와요. mock(지연 0.3배)으로 돌려 보니 캐시 적중이 full 80%, sliding 66%, anchored 74%, 평균 입력이 2,372 / 2,297 / 2,194로 아래 실험 2의 표와 같은 경향이었어요(mock 답변이 표를 만들 때와 달라 숫자는 조금 달라요).

API로도 시작할 수 있어요. `character_id`는 `GET /api/characters`로 확인하세요.

```bash
curl -X POST http://127.0.0.1:8000/api/experiments -H "Content-Type: application/json" -d '{
  "name": "창 전략 비교", "character_id": 2, "persona_name": "민준",
  "inputs": ["안녕하세요", "책 구경해도 돼요?", "이 서점은 언제 생겼어요?"],
  "variants": [
    {"label": "full", "settings": {"window_strategy": "full", "input_token_budget": 3000}},
    {"label": "anchored", "settings": {"window_strategy": "anchored", "input_token_budget": 3000}}
  ],
  "reset_mock": true, "seed": 7, "wait_summary": true, "cooldown_seconds": 0
}'
```

## 실험 가이드

mock으로도 대부분 해 볼 수 있어요. mock의 숫자는 흉내 낸 값이니, 경향을 확인한 뒤 실제 모델로 검증해 보세요.
설정을 비교하기 전에는 **비교** 탭의 **mock 캐시 비우기**를 눌러 앞선 실험의 캐시를 지우세요.

### 1. 프롬프트 캐시는 어디서 적중하나

1. 하람과 새 대화를 열고 서너 번 주고받아요. 오른쪽 **실제 입력 토큰**에서 '캐시에서 읽음' 비율을 봐요. 첫 턴은 0%(쓰기만), 다음 턴부터 오르는 게 정상이에요.
2. **다시 생성**을 눌러요. 같은 프롬프트라서 '캐시 안 됨'이 0에 가까워져요(마지막 입력 끝의 중단점 덕분).
3. 설정에서 **캐시 방식 → 자동**으로 바꾸고 몇 턴 더 보내 보세요. 읽기가 0에 머물고, 쓰기 비용(1.25배) 때문에 캐시를 끈 것보다 오히려 비싸져요.

왜 그럴까요? 이 앱은 매 턴 마지막 사용자 메시지에 로어와 지시(시스템 메모)를 붙여요. 자동 캐시는 마지막 블록에만 중단점을 두는데, 다음 턴에는 그 메시지가 메모 없이 다시 들어가서 서버가 저장해 둔 앞부분과 내용이 달라져요.
명시적 방식은 메모가 붙기 전인 '직전 대화 끝'에도 중단점을 둬서 이 문제를 피해요. 자동 캐시를 쓰려면 지난 턴의 메시지를 고치지 않는(append-only) 구조여야 해요.

### 2. 창 전략 비교: full, sliding, anchored

1. 설정에서 **입력 예산을 3000**으로 줄여요(차이가 빨리 보여요).
2. 창 전략을 하나 고르고 새 대화에서 15턴쯤 보낸 뒤, 전략을 바꿔 새 대화에서 같은 걸 반복해요.
3. **비교** 탭과 답변 아래의 캐시 비율을 봐요.

전략을 바꿀 때 설정의 **실험 라벨**도 `full`, `anchored`처럼 바꿔 두면 비교 탭에서 라벨 이름으로 행이 나뉘어 알아보기 쉬워요.
손으로 보내는 대신 위의 **대본 재생 실험**(실험 2 예시 채우기)으로 세 전략을 한 번에 돌릴 수도 있어요.

mock으로 하람과 16턴을 보냈을 때의 예(입력 예산 3000, 명시적 캐시, 실험마다 mock 캐시를 비움). 같은 조건에서 캐시 방식만 자동으로 바꾸면 적중 0%에 비용은 캐시를 끈 것보다 20% 높았어요.

| 전략 | 평균 입력 | 캐시 적중 | 턴별 모습 |
|---|---|---|---|
| full | 2,475 | 77% | 앞부분이 늘 같아서 적중률이 높지만 입력이 계속 늘어요 |
| sliding | 2,400 | 61% | 창이 밀리기 시작하면 매 턴 대화 앞부분이 바뀌어 40%대로 떨어져요 |
| anchored | 2,258 | 71% | 요약 직후 한 턴만 50%로 떨어졌다가 바로 70%대로 돌아와요 |

대화가 짧으면 full + 캐시가 가장 싸게 나올 수도 있어요. 대화가 길어질수록 full은 입력이 끝없이 늘고, anchored는 입력이 일정 범위에 머물러요.
입력 예산을 고정 프롬프트 크기에 너무 가깝게 잡으면 요약이 자주 일어나서(요약이 바뀔 때마다 그 뒤 캐시가 깨짐) 오히려 손해예요.

### 3. 요약 메모리가 무엇을 잊나

1. anchored에서 입력 예산을 3000으로 두고, 초반에 구체적인 사실(이름, 약속, 물건)을 몇 개 말해 둬요.
2. 대화를 이어 가다 요약이 생기면(**요약** 탭) 그 사실을 물어봐요.
3. `prompts/summary_system.txt`의 '[고정 사실]' 지시를 빼고 다시 해 보며 차이를 봐요.

요약은 답변이 끝난 뒤 백그라운드에서 만들어지고, 대화 가지마다 따로 적용돼요(요약이 어느 메시지까지 덮는지 기록해 두기 때문).

### 4. 로어북

- 하람에게 "저 고양이 이름이 뭐예요?"라고 물으면 '먹물' 항목이 마지막 입력에 들어가요(패널의 로어북 칩).
- '움직이는 문장'은 보조 키가 필요한 항목이에요. "자정에 문 닫으세요?"로는 안 걸리고, "자정이 되면 책 글자가 움직인다던데"처럼 보조 키(문장, 글자, 종이 위)가 최근 대화에 함께 나와야 걸려요.
- 키워드는 부분 문자열로 찾아요. 그래서 보조 키를 '종이'로 두면 인사말의 "종이 울린다"(종 + 조사 '이')에도 걸려요. 조사가 붙는 한국어에서 흔한 오탐이라 샘플에서는 '종이 위'로 좁혀 뒀어요. `/종이(?! 울)/`처럼 슬래시로 감싸면 정규식 키로 쓸 수 있어요.
- 설정에서 **로어 예산**을 150으로 줄이고 여러 키워드를 한꺼번에 말하면, 우선순위가 낮은 항목부터 빠지는 걸 볼 수 있어요.

### 5. 검수: 안전과 속도의 교환

- **출력 버퍼**를 '문장 단위'와 '바로 표시'로 바꿔 가며 `/mod-test-output`을 보내 보세요. 문장 단위는 문제 문장이 화면에 나가기 전에 멈추고, 바로 표시는 다 보여 준 뒤에 가려요. 대신 패널의 **첫 표시** 시간이 문장 단위 쪽이 늦어요.
- 출력 버퍼를 바꿀 때 **실험 라벨**을 `문장`, `바로`처럼 붙여 두면 비교 탭의 **첫 표시** 칸에서 두 방식을 바로 비교할 수 있어요.
- **검수 방식 → llm**은 규칙에 걸리지 않은 글을 LLM이 한 번 더 판정해요. 입력 검수 지연이 그만큼 늘어나는 걸 확인해 보세요. 판정 호출의 비용은 이번 턴 탭의 비용 블록과 비교 탭의 비용 칸(검수 N회)에 따로 나와요. 판정 프롬프트는 `prompts/judge.txt`예요.
- 검수에 막힌 입력은 다음 턴 프롬프트에도 들어가지 않아요(막아 놓고 다음 턴에 슬쩍 들어가는 구멍을 막기 위해).
- 자해·자살 신호가 입력에서 보이면, 검수 모드가 off가 아닌 한 캐릭터 대화를 멈추고 상담 번호를 안내해요(`prompts/crisis.txt`).
- `moderation_rules.json`의 규칙은 일부러 단순해요. "배고파 죽겠다" 같은 과장 표현이 걸리는지(오탐), 돌려 말한 표현이 빠지는지(미탐) 검수 로그로 확인하며 다듬어 보세요. 파일을 저장하면 바로 반영돼요.

### 6. 토큰 추정 보정

예산 계산은 추정치로 해요(제공사마다 토크나이저가 달라서). 실제 모델로 몇 턴 보낸 뒤 패널의 **추정 대비 실측** 값을 보고 `.env`의 `TOKEN_HANGUL_RATIO`를 맞춰 보세요. 같은 한국어 문장도 모델마다 토큰 수가 꽤 달라요.

### 7. 로컬 모델의 첫 토큰 시간

Ollama 같은 로컬 서버는 사용량에 캐시 토큰을 보고하지 않는 경우가 많지만, 앞부분이 같으면 KV 캐시를 재사용해서 첫 토큰이 빨라져요.
anchored와 sliding을 번갈아 써 보며 **첫 토큰** 시간이 어떻게 달라지는지 비교해 보세요.

### 8. 작은 로컬 모델과 사고

같은 모델도 Ollama에서 직접 짧게 물을 때와 이 앱에서 롤플레이를 시킬 때 답의 질이 크게 달라요. 앱은 매 턴 1,000토큰이 넘는 한국어 규칙·캐릭터 설정·대화 기록을 함께 보내기 때문이에요.

1. `.env`에서 `OPENAI_COMPAT_REASONING_EFFORT`를 비우고(사고 켬) 하람과 몇 턴 보내 봐요. 답변 아래의 **사고** 시간과 패널의 **사고 분량**을 봐요.
2. `none`으로 바꾸고 서버를 다시 시작한 뒤 같은 입력을 보내요.
3. 설정에서 모델만 더 큰 것으로 바꿔 같은 걸 반복해요.

.env의 사고 설정은 턴마다 실행 조건으로 기록돼서 비교 탭에서 저절로 행이 나뉘어요. **실험 라벨**을 `사고 켬`, `사고 끔`처럼 붙여 두면 어느 행인지 알아보기 쉬워요.

하람 첫 턴의 요청 원문을 그대로 다시 보낸 예(Ollama 0.40.3, RTX 5060 Laptop 8GB, 조건마다 2번):

| 모델 | 사고 | 걸린 시간 | 결과 |
|---|---|---|---|
| qwen3.5:2b | 켬 | 73~110초 (사고 2만~3만 자) | 2번 중 1번은 최대 출력 8000을 사고에 다 써서 빈 답, 나머지도 앞뒤가 안 맞음 |
| qwen3.5:2b | 끔 | 3~5초 | 한자·영어가 섞이고 인물의 성별·말투가 흔들림 |
| qwen3.5:4b | 끔 | 4~16초 | 장면을 따라가고 존댓말 유지, 가끔 외국 글자 한 자 |

작은 모델은 이상한 답이 대화 기록에 한 번 들어가면 그 서식이나 말버릇을 다음 답에서 따라 해서 점점 더 무너져요. 이상한 답은 **다시 생성**하거나 고쳐 두세요.

비교 탭(또는 대본 재생 실험)의 외국 문자·말투 변화·반복 칸으로 모델과 사고 설정을 비교해 보세요. 같은 대본을 모델이나 사고 설정만 바꾼 변형으로 돌리면, 위 표의 "한자·영어가 섞임", "말투가 흔들림", "따라 해서 무너짐"이 행마다 숫자로 나와요.

실제로 같은 12턴 대본을 qwen3.5 2b·4b, exaone3.5 7.8b, kanana 3.5b(모두 사고 끔)에 돌려 보면 이런 차이가 숫자로 나와요(2026-11-03, 실험 한 번에 약 9분 30초). 2b는 12턴 중 11턴에서 마지막 입력에 붙은 `<system-memo>`를 대사에 따라 썼고(프롬프트 샘), qwen 두 모델은 한자가 한두 글자씩 끼는 턴이 4~5턴인데 exaone과 kanana는 한 번도 없었어요. kanana는 한 문장 틀을 되풀이해서 직전 답 겹침이 평균 22%(나머지 5~12%)였고 말투도 존댓말과 반말을 오갔어요. 같은 대본의 첫 3턴을 4b에 사고를 켜고 돌려 보면(`OPENAI_COMPAT_REASONING_EFFORT` 비움, 최대 출력 8000) 외국 문자가 한 번도 안 끼고 깃발도 없었지만, 사고가 9천~3만 자라 턴당 4분 20초~11분 걸렸어요(표본이 3턴뿐이에요). 표와 해석은 `docs/improvement-plan.md`의 "후속 보강"에 있어요.

같은 대본을 변형마다 2회씩 반복하며 프롬프트와 샘플링 값을 바꿔 보면, 회차 사이 차이가 변형 사이 차이보다 큰 경우가 많아요(2026-11-10, Ollama 0.40.16). 2b의 `<system-memo>` 샘은 96턴 동안 한 번도 재현되지 않았고, 대신 한 회차에서 `<br>`·`<sup>` 같은 HTML 태그를 넣기 시작해 11턴 동안 따라 했어요. `top_p`·`presence_penalty`를 Modelfile 값으로 맞춘 변형도 같은 조건의 두 회차가 외국 글자 2자와 25자로 갈렸어요. 작은 모델은 이상한 답을 한 번 내면 그 뒤를 따라 하기 때문에, 한 번 돌린 결과로 설정을 판단하지 말고 **반복**해서 반복 사이 편차를 함께 보세요. 표와 해석은 `docs/improvement-plan.md`의 "다음 단계"에 있어요.

## 구조

```
charchat-lab/
├─ run.py                   실행 진입점
├─ app/
│  ├─ main.py               FastAPI 라우트
│  ├─ chat_service.py       한 턴의 흐름: 입력 검수 → 조립 → 스트리밍 → 사후 검수 → 저장 → 요약 예약
│  ├─ runinfo.py            턴과 요약에 남기는 실행 조건(설정, .env 옵션, 프롬프트 파일 지문)
│  ├─ experiments.py        대본 재생 실험(입력 목록을 변형마다 새 대화로 자동 재생)
│  ├─ quality.py            답변 품질 어림 지표(외국 문자, 말투 변화, 반복)
│  ├─ prompt.py             프롬프트 조립과 창 전략(full/sliding/anchored)
│  ├─ memory.py             요약 메모리(덩어리 요약, 백그라운드 실행)
│  ├─ lore.py               로어북 매칭(키, 보조 키, 정규식, 예산)
│  ├─ moderation.py         규칙/LLM 검수, 문장 단위 출력 버퍼
│  ├─ cards.py              캐릭터 카드 V2/V3 JSON·PNG 가져오기, 내보내기, 매크로
│  ├─ db.py                 SQLite. 메시지는 트리(parent_id)로 저장
│  ├─ tokens.py             토큰 추정
│  ├─ pricing.py            비용 계산(Claude 가격 내장, pricing.json으로 추가)
│  └─ providers/            mock, anthropic, gemini, openai_compat 어댑터
├─ prompts/                 프롬프트 템플릿(저장하면 다음 요청부터 반영)
├─ characters/              처음 실행할 때 넣는 샘플 카드
├─ moderation_rules.json    검수 규칙
├─ static/                  화면(빌드 없는 HTML/CSS/JS)
└─ tests/                   pytest
```

한 번의 요청은 이렇게 생겼어요. 잘 안 바뀌는 것을 앞에, 자주 바뀌는 것을 뒤에 둬요.

```
system    [고정] 규칙 + 캐릭터 카드 + 페르소나 + 상시 로어 + 예시 대화   ← 캐시 중단점 ①
          [요약] 지금까지의 줄거리                                       ← 캐시 중단점 ②
messages  (대화 시작 자리표시자) + 최근 대화                             ← 직전 대화 끝에 중단점 ③
          마지막 사용자 메시지 = 입력 + <system-memo>(로어, 진행 지시)    ← 중단점 ④
```

메시지는 트리로 저장돼요. 다시 생성이나 수정은 같은 부모 밑에 형제를 하나 더 만들고, 채팅의 `active_leaf_id`에서 루트까지 거슬러 올라간 경로가 지금 보이는 대화예요.

## 고쳐 보기 좋은 곳

- `prompts/main.txt`: 기본 규칙. 캐릭터 카드의 시스템 프롬프트에 `{{original}}`을 쓰면 이 내용이 그 자리에 들어가요.
- `prompts/post_history.txt`: 매 턴 마지막 메시지에 붙는 지시
- `prompts/final_user.txt`: 마지막 메시지의 모양(입력과 시스템 메모의 배치)
- `prompts/summary_*.txt`, `prompts/judge.txt`: 요약과 LLM 검수 프롬프트
- `moderation_rules.json`: 검수 규칙
- `pricing.example.json`을 `pricing.json`으로 복사해서 다른 모델 가격 추가. `input`/`output`이 null이거나 가격표에 없는 모델은 비용을 계산하지 않고 '가격표 없음'으로 보여요(로컬 모델은 0을 적으면 0으로 계산해요)

## API

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/api/config` | 제공사 상태, 설정, 설정 명세 |
| PUT | `/api/settings` | 런타임 설정 변경(`models`, `provider_options`, `prompt_overrides`는 저장된 값에 합치고, 항목을 `null`로 보내면 지워요) |
| GET/POST | `/api/characters` | 캐릭터 목록, 만들기 |
| POST | `/api/characters/import` | 카드 파일(JSON, PNG) 가져오기 |
| GET | `/api/characters/{id}/export` | V2 카드 JSON 내보내기 |
| POST | `/api/chats` | 대화 만들기 |
| GET | `/api/chats/{id}` | 지금 경로의 메시지와 형제 정보, 요약 상태 |
| POST | `/api/chats/{id}/messages` | 보내기(SSE 스트림) |
| POST | `/api/chats/{id}/regenerate` | 다시 생성(SSE) |
| POST | `/api/chats/{id}/switch` | 다른 가지로 이동 |
| POST | `/api/messages/{id}/edit` | 수정(사용자 메시지는 SSE, 캐릭터 메시지는 JSON) |
| POST | `/api/chats/{id}/summarize` | 지금 요약 |
| GET | `/api/chats/{id}/stats` | 실행 조건별 사용량·비용 비교(요약·검수 판정 비용 포함, `varying`은 행마다 다른 조건) |
| GET | `/api/messages/{id}/prompt` | 그 턴에 보낸 요청 원문 |
| POST | `/api/experiments/estimate` | 시작하기 전에 변형별 호출 수와 비용 상한, 캐시 섞임 경고를 어림(실험을 만들지 않음) |
| POST | `/api/experiments` | 대본 재생 실험 시작(한 번에 하나, 실행 중이면 409) |
| GET | `/api/experiments` | 실험 목록(최근 순, 대본은 개수만) |
| GET | `/api/experiments/{id}` | 실험의 진행 상황과 변형별 결과 비교(`stats`) |
| POST | `/api/experiments/{id}/cancel` | 실험 취소 |
| DELETE | `/api/experiments/{id}` | 실험 기록 삭제(만든 대화는 남음) |
| GET | `/api/experiments/{id}/export.csv` | 결과 비교 표를 CSV로 |

SSE 이벤트: `user`, `meta`(조립 결과), `thinking`(사고 진행: 글자 수, 시간), `delta`, `reset`(사고가 답변으로 샌 부분을 지움), `retract`(검수로 가림), `notice`(입력 차단, 위기 안내), `error`, `done`.

## 테스트

```bash
.venv/bin/pip install -r requirements-dev.txt     # Windows: .venv\Scripts\python -m pip install -r requirements-dev.txt
.venv/bin/python -m pytest
```

API 키 없이 돌아가요. 제공사 어댑터는 실제 SDK(anthropic, google-genai, openai)를 가짜 HTTP 서버에 붙여서, 보내는 요청 형식과 스트림 해석을 검증해요. GitHub에서는 main에 push할 때와 PR마다 같은 테스트가 자동으로 돌아요(`.github/workflows/tests.yml`).

## 주의할 점

- 서버는 기본으로 `127.0.0.1`에서만 열려요. API 키가 서버에 있으니 외부에 열지 마세요.
- mock의 캐시, 지연, 비용은 흉내 낸 값이에요. 비용표의 Claude 가격은 2026-10-12에 공식 문서에서 확인한 값이라 바뀔 수 있어요.
- 기본 설정은 전체이용가 기준(검수 block, Gemini 안전 필터 켬)이에요.
